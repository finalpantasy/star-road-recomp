All 2675 jump-table functions were relifted and recompiled. This bug could have hit any computed switch in the game.

### Follow-on: applet, account and nvdrv boot path (lead step list: applet, shader cache v1)
- **Controller-support applet** (`runtime/hle/hle_applet.c`): `ILibraryAppletCreator` cmd 0 creates an `ILibraryAppletAccessor` (applet id 0x0C); the guest pushes its storages, `Start` answers at once with the reply a console with one connected controller gives (player count 1, selected id 0 = handheld, result 0), and `GetResult`/`PopOutData` hand it back through `IStorage` -> `IStorageAccessor`. No permissive mode. The game calls it twice (about 10 s apart) and goes on.
- **Auto-select buffers.** A guest `Read`/`Write` on a storage (and nvdrv ioctls) sends the buffer as both a map-alias and a pointer descriptor, one of them empty. `ipc_in_data_idx` / `ipc_out_data_idx` (`hle_ipc.c`) pick the half that carries bytes. The first controller-applet reply was read into a zero-size buffer before this.
- **Launch parameter.** `IApplicationFunctions` cmd 1 `PopLaunchParameter(kind)`: kind 2 (PreselectedUser) is the 0x88 byte storage (magic 0xC79497CA, byte 1 at +4, 16 byte user id at +8); every other kind answers 0x480 (`MAKE_RES(128, 2)`, "no data"). The sdk treats 0x480 as none and aborts on any other nonzero result. Cmd 22 `SetTerminateResult` logs. Without the kind-2 storage `nn::account::TryOpenPreselectedUser` fails and the managed code aborts.

### Follow-on: what Loading waited on (lead step list: Loading, interpreter misses)

### Follow-on: thread-53 stack fault and the movie path (lead: stack fault, then what the movie path needs)
- Cause of the exit 5 / memset fault: not stack allocation. The game creates CriManaDecodeThread itself (pthread-like wrapper 0x7101452160 called from main+0x14fc380, name string at 0x71029fae31) with a hard-coded 16 KiB stack (svcMapMemory dst=0x74a1b1a000, top 0x74a1b1dfe0). A CRI native callback (cri_native 0x14510a0) calls a CRI C# callback (cri_csharp 0x19d7b00) on that thread; the managed path reaches BCL 0x710179d6b0, which does a 16 KiB stackalloc (`sub x19, sp, #0x4000; memset`). That overflows a 16 KiB stack by about 0x770 bytes. Horizon would fault too, so real hardware never takes this path; it runs when the nvdec or nvhost interaction fails or is unsupported (unknown ioctls 0xc0a40009, 0xc0a4000a, 0xc1bc0001, 0xc0400001 on /dev/nvhost-nvdec, 0xc010001e and friends on /dev/nvhost-ctrl).
- Second layer: after the fault is absorbed, nn::diag::GetBacktrace calls os::GetCurrentStackInfo (sdk 0x12ebb0), which compares sp with the ThreadType's recorded stack (base at +0x50, size at +0x58; ThreadType = [tpidrro_el0+0x1f8]) and aborts through svcBreak (exit 3) if sp is outside.
- STOPGAP 1, svc.c `svc_stack_grow` (always on; SMRPG_NO_STACKGROW=1 disables): an access violation just below a registered thread stack mapping (within 256 KiB) commits the pages, and patches the ThreadType base and size so the SDK check passes. QueryMemory reports the grown region as one stack. Logged as "STOPGAP stack growth". It hides a guest bug that only exists because of STOPGAP 2's cause; remove it once nvdec is answered for real.
- STOPGAP 2, hle_gfxsvc.c (SMRPG_NVDEC_OK=1, off by default): the four nvdec ioctls and every nvhost-ctrl ioctl answer success with no decode. Logged as "STOPGAP nvdec ioctl ..." and "STOPGAP nvhost-ctrl ioctl ...". No decoder is built (the decoder library is the owner's license call).
- Debug aids added: SMRPG_STKLOG (MapMemory, QueryMemory above the stack base, CreateThread frames), SMRPG_STACKSTR=1 (printable runs above sp at a crash), SMRPG_FSLOG=1 (paths passed to nn::fs OpenFile, GetEntryType, GetFileSize), crash line "guest pc is HLE slot NAME", SMRPG_DUMPADDR text dump.
- Movie path evidence (SMRPG_FSLOG): the game opens `rom:/Data/StreamingAssets/movies/movie_017.usm` at about 12 to 13 s (right after the unity_builtin_extra and resources.assets reads), then `movie_001.usm` at about 28 s in the runs that survive.
