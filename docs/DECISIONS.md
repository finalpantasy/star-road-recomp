## D-010: Start from the released SMRPG recomp, build our own beside it
- Date: 2026-11-24. Decided by: the owner ("start with the currently already released builds ... then make our own coded stuff on the side too").
- Decision: ElKiro1311/smrpg-recompiled (MIT, LASRecomp base, plays 1.0.0 start to finish) becomes our playable baseline now. We build it from source on A: from the owner's 1.0.0 dump and use it three ways: to play and capture frames now, as a reference oracle (frames, service traces, timing) for our own recompiler and runtime, and as a reuse source under D-009 (its code stays out of our Git until rewritten). Our own tracks (task-10, task-13, task-14) continue in parallel.
- Why: images and a playable game today instead of after the first frame of our own runtime; a working reference speeds up every subsystem test.
- Limits: it targets 1.0.0 only; 1.0.1 support is ours to add. No prebuilt installer or release binary is run; everything is built from source.

## D-011: Movie decoding through FFmpeg as a separate LGPL DLL
- Date: 2026-11-25. Decided by: the lead, on the owner's delegation ("Up 2 u").
- Decision: VP9 video (and Opus audio if the movies need it) is decoded by FFmpeg's libavcodec, loaded as a separate LGPL-only DLL (no GPL or nonfree parts), built from source on A: by a script we commit. Our code only calls its public API. No FFmpeg source or binary enters Git. The release ships the DLL beside the exe with its license and a pointer to the source. The HLE boundary stays the one in docs/RECOMPILER.md: `nn::movie` (subsdk0, 31 imports) is replaced by our HLE, which hands compressed frames to libavcodec.
- Why: the title screen needs decoded movies now; libavcodec's VP9 decoder is mature and fast; the released baseline already shows the route works. Our own VP9 decoder is weeks of work for no visible gain, and dynamic linking keeps our own license free.
- Rejected: our own VP9 decoder (cost, risk); answering the nvdec ioctls with a full NVDEC emulation (more surface than the 31 `nn::movie` imports).
- Revisit if: the owner wants zero third-party binaries in the release, or LGPL terms conflict with how the release is packaged.
- Update 2026-11-25: the owner: "ffmpeg inclusion is fine - just include it". Development uses the FFmpeg DLLs already on A: (MSYS2) for speed; the minimal LGPL-only build is deferred to release packaging (a release card), so the shipped DLL does not pull GPL terms onto our code.

## D-012: Third-party libraries are welcome; other recomps' code is not
- Date: 2026-11-25. Decided by: the owner ("include 3rd party things for now, we'll slowly replace them"; "ffmpeg inclusion is fine - just include it"; "ffmpeg can stay in there for... ever... i just don't want stuff people recomped in"; "Yes, keep it out").
- Decision: general third-party libraries (FFmpeg first; also SDL, Vulkan loader and the like) may stay in the runtime permanently. They are listed under "Third-party libraries" in `docs/REUSE_LEDGER.md` with their license, need no replacement card, and their binaries are not committed (loaded from A: in development, shipped beside the exe with license files at release).
- What stays out: code taken from other recomp and emulator projects (ElKiro's SMRPG recomp, LASRecomp, the Snap recomp harness, Ryubing and similar). Under D-009 it lives only in gitignored `reuse/` and on A:, is never committed or pushed, and is replaced by our own code before release.
- Release note: ship an LGPL-only FFmpeg build so its terms do not reach our own code.

## D-013: Rust decomp leaves default on
- Date: 2026-11-26. Decided by: the owner ("yes" to accepting task-29).
- Decision: `SMRPG_DECOMP` defaults to `on`; the three Rust integer leaves replace their lifted bodies. `off` and `ab` stay available.
- Why: 10,125 randomized comparisons per function and live A/B calls (Min, Max, is_in) all showed 0 differences.
- Revisit if: a leaf is found to differ from the original in a new scene; run `ab` first.
